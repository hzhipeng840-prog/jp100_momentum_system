# バージョン管理規約

## 目的

機能、評価条件、データ構造、運用方法の変更を、`v1`、`v2`、`v3`のような単純な連番で追跡します。連番は`v100`以降も継続できます。

## 管理対象

- `VERSION`: 現在の正式バージョン。
- `CHANGELOG.md`: 全バージョンの要約。
- `docs/versions/vN.md`: そのバージョンの目的、変更、互換性、検証結果。
- Gitコミット: 実装差分の完全な履歴。
- Gitタグ `vN`: GitHub上で正式版を固定するタグ。
- `metadata.json`: 生成データが使用した `app_version` と `run_id`。

## 新しいバージョンを作る手順

1. 作業開始前に変更目的と完了条件を決める。
2. `scripts/new_version.ps1` を実行し、次の連番を作る。
3. 実装とテストを行う。
4. `CHANGELOG.md` と `docs/versions/vN.md` を具体的な内容へ更新する。
5. `scripts/verify.ps1` を実行する。
6. 変更をコミットする。
7. 正式公開時に同じ番号のGitタグを付けてGitHubへプッシュする。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/new_version.ps1
```

## バージョンを上げる変更

- 評価式、重み、フィルター、毎日厳選条件の変更。
- データソース、取得時刻、基準日、売買想定の変更。
- CSV、JSON、履歴、スナップショット構造の変更。
- 新しい画面、回測、通知、定期処理の追加。
- 利用者が結果の意味を異なるものとして解釈する可能性がある修正。

誤字修正や内部テストだけの変更は、同じバージョン内のコミットとして記録できます。ただし利用者への影響がある場合は `CHANGELOG.md` を更新します。

## 禁止事項

- 過去の `docs/versions/vN.md` を現在の仕様に合わせて書き換えない。
- 公開済みタグを別のコミットへ付け替えない。
- 同じ番号を異なる評価条件へ再利用しない。
- `VERSION` だけを変更し、変更履歴と検証結果を空のまま公開しない。
